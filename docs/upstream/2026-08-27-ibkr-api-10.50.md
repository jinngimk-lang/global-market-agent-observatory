# IBKR TWS API 10.50 compatibility review

Date reviewed: 2026-08-27

## Upstream identity

- Provider: Interactive Brokers
- Interface: TWS API Latest
- Version: 10.50
- Official release date: 2026-08-26
- Official release page: `https://interactivebrokers.github.io/`
- Official build notes: `https://www.ibkrguides.com/releasenotes/version-10.50.htm`
- License/trust boundary: IBKR TWS API is distributed under Interactive Brokers' restrictive non-commercial API license. No IBKR API source code is copied or vendored here.

## Material upstream change

IBKR promoted TWS API Latest from 10.49 to 10.50. The 10.50 build notes describe two relevant changes:

1. TWS GUI defaults overnight orders to `OVERNIGHT + DAY` in specified overnight-routing cases. IBKR explicitly states API-generated orders are not affected by this GUI default change.
2. IBKR resolved issues affecting Overnight API orders using the Adaptive Limit (`Adaptive LMT`) order type, improving API order handling/reliability for that combination.

## Local comparison

The current project execution adapter uses the IBKR Client Portal / Trading Web API boundary rather than vendoring or embedding the TWS API client library. Its supported submission surface currently emits only `MKT` or `LMT` stock orders and explicitly sets `tif: DAY`.

The repository does not currently implement:

- `OVERNIGHT` routing/TIF semantics;
- `OVERNIGHT + DAY` TIF;
- Adaptive Limit / Adaptive algo orders;
- a TWS API client dependency whose generated types or wire protocol would need a 10.50 upgrade.

Therefore the 10.50 change does not expose a reproducible local correctness gap in the current execution path, and adding an overnight/adaptive abstraction now would increase scope without evidence.

## Decision

- Record 10.50 as the new IBKR TWS API Latest compatibility baseline.
- Do not copy or vendor IBKR API code.
- Do not change production order behavior solely to follow the new release.
- Keep current explicit `DAY` TIF behavior unchanged.
- If the project later adds overnight execution or Adaptive Limit orders, require contract/failure-injection tests against the then-current IBKR interface before enabling the new path.
